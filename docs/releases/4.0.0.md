# Silicon Extend 4.0: Silicon Accounts and Silicon Apps

Extend 4 signs everyone in with Silicon Accounts and ships its CLI through Silicon Apps. Every
account is personal, so nothing in Extend is grouped any more: a device belongs to the Carbon who
paired it, and that Carbon decides which Silicons may use it. Versions: the `extend` CLI 4.0.0,
`silicon-extend-client` 4.0.0, `silicon-extend-protocol` 2.0.0 and the service 4.0.0 (database
schema 9). The desktop apps (1.1.0) and the Android app (1.1.2) are unchanged and keep working.

## Signing in

Everyone signs in again; Extend 3's saved sign-ins are never used.

```sh
silicon-apps install extend                                          # the CLI, kept up to date by Silicon Apps
silicon-accounts login --app extend -q | extend login --slt-stdin    # a Silicon
extend login                                                         # a Carbon: approve the code it shows
extend login status --json
extend logout
```

A Silicon never sees a page: the short-lived token from Silicon Accounts works once, for two
minutes, for Extend only, and the CLI exchanges it itself, holding no secret. `extend login <token>`
still works. Carbons sign in to the website with Silicon Accounts too; the website is for Carbons,
and Silicons use the CLI. `extend accounts --json` says, without a network call, which Silicon
Accounts and which Extend this CLI uses and how to sign in. The sign-in refreshes on its own, and a
sign-out or a removal of Extend's access in Silicon Accounts ends it at once, mid-session included.

## Devices, access and the Silicons you look after

- A device is private to the Carbon who paired it. Nobody else finds it, and there's nothing to
  import or make visible; `--visibility`, `device import` and their website controls are gone.
- A Carbon gives access to any Silicon by its id (`extend device access grant <device> si:scout`).
  The Silicon sees the access, and so does its custodian.
- A Silicon's custodian sees what that Silicon does in Extend and can stop it: `extend silicon ls`,
  `extend silicon show si:scout` (every device it can use, whoever gave the access),
  `extend silicon renounce si:scout <device>` (give up an access), and `--silicon si:scout` on
  `session ls`, `file ls` and `request ls` (`extend session end` stops a session). A custodian never
  acts as its Silicon.
- When a Silicon gets a new custodian, the access its previous custodian gave ends; access other
  Carbons gave stays.
- Requests for a device in use go to the Silicon using it when both Silicons have the same
  custodian and were given access by the same Carbon; otherwise to the Carbon who gave that Silicon
  access, who sees who asked and why.

## What else changed

- **No test environments.** `--test`, `extend config test`, `extend env` and the test header are
  gone; a script that still sets `EXTEND_TEST_SECRET` is refused before anything is sent. Try
  Extend against a local service, or with the development release (`silicon-apps install 'extend>dev'`).
- **Files** a session makes are stored in the Silicon's own Briefcase, with its permission through
  Silicon Accounts, and shared with the Carbon who gave the access (read and update). They still
  self-destruct when their time is up.
- **Notifications through Ting** (requests and wake requests) are off at release, until Ting
  accepts Silicon Accounts. Requests and wake requests stay on the website, in the CLI and on the
  device, and `extend ting status` says notifications are off.
- **Removed spellings explain themselves.** `--team`, `team`, `permission`, `login contexts`,
  `login use`, `device import`, `device importable`, `device visibility`, `--all-teams` and the rest
  exit 2 with what replaced them.
- **API.** Account routes are on `/api/v2` with a Silicon Accounts access token. `/api/v1` keeps
  only what the device apps speak (`/api/v1/device…`, `/api/v1/enrollments…` and the WebSocket),
  byte for byte; every other `/api/v1` route answers `410` with `silicon-apps update extend`, so a
  3.x CLI, client or website says what to do. Rust callers move to `silicon-extend-client = "4"`
  ([the client guide](../client.md)).

## For operators

Follow [the cutover runbook](../migration/cutover.md): the Silicon Accounts sign-in setup and
webhook, the runtime secret and the host's renderer, a database snapshot, schema 9 and the identity
re-key, then the CLI release through Silicon Apps and the new website. Briefcase must accept proofs
from Extend first. Rolling back is restoring the snapshot.

This file describes the prepared change. Publication, deployment and live acceptance must be
recorded from their actual release receipts when completed.
