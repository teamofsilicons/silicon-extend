# Silicon Extend 1.1.0

Several Carbons can now pair the same device while retaining separate access controls. Extend coordinates one active session per physical device, supports grants across a Carbon's Teams, and adds wake requests and clearer setup retry controls.

The desktop “is using this device” banner can be moved, collapsed and restored. Shared banner preferences and timed announcements carry through the service, website and device apps. This release also fixes iOS capture and alias cleanup, stale carried-device names and reconnect state, Android TV image readiness and memory use, and Briefcase media display. Keyed requests reserve execution and retain their results; uncertain interrupted operations require reconciliation.

## Upgrading

- API v1 and existing 1.0 credentials remain compatible. The 1.1 service must be deployed before clients and device apps.
- Devices previously made visible to a Team become personal to the Carbons who paired them; colleagues need explicit grants.
- A Carbon's logout ends their Silicons' sessions. On a computer paired by several Carbons, terminal access belongs to the installer's Silicons.
- Add a shared TV through one host computer. Adding the same TV through a second computer leaves the later copy not ready.
- Keep the existing app signing identity when upgrading. The macOS download is signed, Apple-notarized and stapled; Android uses the existing release certificate.

## Known limitations and verification coverage

- Automatic Briefcase sharing can fail when the recipient Carbon has never used Briefcase. The uploaded file is retained and the sharing error is reported. IAM/OBO remains unchanged in this release.
- Android 10 phone passed 42 multi-session checks and 18 of 20 native checks, including a recording with 187.251 seconds reported duration and a frame after 182 seconds. The detached-process enumeration assertion and burst-recording duration assertion failed; the latter reported 5.9 seconds against 8.272 seconds of wall time. Retained frame counts do not establish lost frames, and the timing cause remains unresolved. Media decode/visual verification was not completed for this round, and reconnect recovery stopped when its test process-termination command failed.
- Android 10 TV native verification is blocked by an ADB authorization/control-connection problem in the stock emulator image. Emulator evidence does not establish physical TV behavior.
- Windows ARM64 GUI input/capture remains unverified because the hosted runner's Windows privacy setup screen blocks the owned test window. Its release lane passed 205 checks (177 unit, 27 fake-service and one native terminal check) and explicitly records that GUI verification was omitted.
- Physical iPhone capture and the remaining iPad owner-alias, long-session/idle-cleanup and reconnect scenarios are unverified. A real iPad screenshot and nine-second recording passed; those checks do not prove the other scenarios.
- Physical multi-monitor, sleep/lock/UAC, macOS banner dragging and the remaining physical desktop/phone/TV matrix are unverified. Automated macOS controls, Linux X11 drag/collapse/restore/Stop and Android API34 TV announcement checks passed.

Detailed source attribution, checks and limits are recorded in `docs/verification.md`. Runtime-equivalent artifacts retain their original build-source identity. SHA-256 checksums are provided with the downloads.
